CMS-OUTAGE — کرش سایت هنگام ورود داده توسط ادمین (Panel Dsh)

تست اینکه ادمین با وارد کردن چه داده‌ای از داشبورد cms.example.test، سایت مصرف‌کنندهٔ site.example.test را به کرش می‌رساند. همهٔ ۲۳ نوع ویجت، فیلدهای فرم، و رفتار بازیابی بررسی شد. روش: No-Cache.

Fail — Blocker

چهار نوع ویجت، در صورت خالی‌ماندن مرجع اجباری، باعث می‌شوند رندر سمت سرور site.example.test با HTTP 500 و بلافاصله 502 (کل سایت) بیفتد — حتی صفحهٔ کاربر عادی و مسیر API. بازیابی خودکار نیست و ۲–۵ دقیقه طول می‌کشد و با تکرار کندتر می‌شود. ریسک قطعی کامل سایت در بلک‌فرایدی با یک ورودی اشتباه ادمین.

ادمین داده وارد می‌کند (مرجع اجباری خالی)→ذخیره با 200 (بدون اعتبارسنجی)→رندر SSR بدون null-guard→استثنای هندل‌نشده→کل پروسه می‌افتد: 500 → 502

باگ‌ها

BUG-01

کرش کامل سایت با ورود دادهٔ ادمین (۴ تایپ، مرجع اجباری خالی)

Blocker · Critical

بازتولید: ادمین ویجتی از نوع Promotion-List / Merchant-Carousel / Voucher-Carousel / Third-Party-Carousel با مرجع اجباری خالی روی دسته‌ای که رندر می‌شود (مثل STORE_1) می‌سازد و فعال می‌کند.

نتیجهٔ واقعی: site.example.test ابتدا HTTP 500 و بلافاصله 502 (کل سرور، همهٔ مسیرها و /api) می‌شود؛ بازیابی خودکار نیست و ۲–۵ دقیقه طول می‌کشد و با تکرار کندتر می‌شود.

اثر: قطعی کامل سایت در پیک (بلک‌فرایدی) با یک ورودی اشتباه ادمین.

اصلاح پیشنهادی: null-guard در رندر SSR برای این تایپ‌ها؛ اعتبارسنجی مرجع اجباری سمت سرور قبل از ذخیره؛ ایزوله‌کردن خطای رندر یک ویجت از کل صفحه/پروسه (try/catch per-widget + fallback).

BUG-02

بازیابی خودکارِ کند و تنزل‌یابنده پس از کرش

Critical · High

بازتولید: بعد از حذف ویجت خراب، زمان بازگشت سایت به 200 اندازه‌گیری شد.

نتیجهٔ واقعی: بازیابی ۲→۴→۵ دقیقه (با هر کرش کندتر)؛ خودترمیمی سریع وجود ندارد.

اثر: حتی پس از رفع داده، سایت دقایقی down می‌ماند.

اصلاح پیشنهادی: health-check و ری‌استارت سریع پروسهٔ SSR؛ جداسازی رندر از پروسهٔ اصلی؛ circuit-breaker.

BUG-03

نبود اعتبارسنجی سمت سرور برای مرجع اجباری/اولویت/موقعیت

Major · High

بازتولید: از API مقادیر نامعتبر برای اولویت، موقعیت و مرجع ارسال شد.

نتیجهٔ واقعی: اولویت منفی/اعشاری/خالی/null و موقعیت خالی/نامعتبر/تکراری/عددی و مرجع خالی همه با 200 ذخیره شدند (فقط اولویت رشته‌ای 400).

اثر: دادهٔ خراب ذخیره و به رندر SSR می‌رسد → ریشهٔ کرش.

اصلاح پیشنهادی: اعتبارسنجی enum و الزام‌ها و نوع‌ها سمت سرور؛ یکتاسازی موقعیت؛ الزام مرجع برای تایپ‌های وابسته.

BUG-04

عدم تقارن اعتبارسنجی UI و API

Major · Medium

بازتولید: قواعدی که UI الزام می‌کند از طریق API دور زده می‌شوند.

نتیجهٔ واقعی: تصویر و marketingId و حداقل موقعیت و فیلتر عددیِ اولویت فقط در UI اعمال می‌شوند؛ API آن‌ها را نادیده می‌گیرد.

اثر: هر کلاینت/اسکریپتی می‌تواند دادهٔ خرابِ کرش‌زا ثبت کند.

اصلاح پیشنهادی: یکسان‌سازی قواعد در لایهٔ سرور.

BUG-05

پذیرش اسکیم javascript: در آدرس redirect

Major · Medium

بازتولید: در فیلد آدرس redirect مقدار javascript:alert(1) وارد شد (UI و API).

نتیجهٔ واقعی: بدون خطا ذخیره شد؛ تگ HTML در عنوان فقط توسط WAF بلاک شد نه اپ.

اثر: ریسک XSS/لینک مخرب در صورت عدم sanitize در رندر.

اصلاح پیشنهادی: allow-list اسکیم (فقط https/deeplink) در UI و سرور + sanitize در رندر.

BUG-06

نبود سقف طول عنوان

Minor · Low

بازتولید: عنوان ۵۰۰۰ کاراکتری در UI و API وارد شد.

نتیجهٔ واقعی: maxlength=99999 و API 5000 را می‌پذیرد.

اثر: داده بیش‌ازحد و ریسک لِی‌اوت/کارایی.

اصلاح پیشنهادی: سقف طول معقول در UI و سرور.

اقدام اصلاحی پیشنهادی (اولویت‌دار)

  • فوری (Blocker): ایزوله‌کردن خطای رندر هر ویجت از کل صفحه/پروسه (try/catch per-widget + fallback) تا یک ویجت خراب کل سایت را نیندازد.
  • فوری: اعتبارسنجی سمت سرور — الزام مرجع برای تایپ‌های وابسته، enum موقعیت/نوع، نوع اولویت. جلوی ذخیرهٔ دادهٔ کرش‌زا را بگیرد.
  • بالا: null-guard در رندر SSR چهار تایپ کرش‌زا؛ و health-check/ری‌استارت سریع برای رفع بازیابی کند.
  • متوسط: یکسان‌سازی اعتبارسنجی UI و API؛ allow-list اسکیم URL؛ سقف طول عنوان.
